# Parity with the product, 2026-10-20

Status: the record of one review, kept current while its fixes landed. On 2026-10-20 the owner
asked that the SDKs match Yogabase as it stands. This file compares each client with the product's
published contracts and with the behaviour of the product's gateway, Control Plane and runtime
routes, says what differed, what was changed here, and what remains. It quotes the product only at
the contract level: the four OpenAPI documents (mirrored byte for byte under `contracts/`) and the
observable behaviour of its routes.

The toolchains the suites ran on are recorded in [`CLOUD_ENVIRONMENT.md`](CLOUD_ENVIRONMENT.md).

## (c) The authored facades against the product's behaviour

Each item was read from the product's route code and its tests, and compared with the clients.

- **Sign-in and PKCE.** `POST /auth/login` answers 204 with the identity cookie, 202 `mfa_required`
  (then `POST /auth/mfa/verify`, 204), 401 `invalid_credentials` for every denial alike, 403
  `mfa_enrollment_required` and 429 `authentication_rate_limited`. The authorization endpoint
  redirects with the code only for a request carrying the cookie, and the token endpoint exchanges
  it with the verifier. External sign-in is `POST /auth/external/{provider}/start`
  (`{redirectUri, codeChallenge}` → `{authorizationUrl, state}`, the redirect URI one the project
  registered and the challenge 43 base64url characters) and `…/callback`
  (`{code, state, codeVerifier}` → 204, or 202 `mfa_required`). The .NET, TypeScript, Python and Dart
  sign-ins follow exactly this; Java now does too.
- **Capability negotiation.** The bootstrap always carries the four core rows; a client names the
  requested-only rows it reads in `X-Yogabase-Accept-Capabilities`, comma separated, matched exactly,
  ignored when unknown or longer than 512 characters in all, and each known one is appended after the
  core rows in the order `realtime-presence`, `data-rest`. The .NET client named only
  `realtime-presence` and accepted at most five rows; it now names both and accepts four to six. The
  TypeScript, Python and Dart sign-ins read the bootstrap for their OIDC fields only and gate nothing
  on a row, so they need no header.
- **Preconditions and idempotency.** Schedules use `If-None-Match: *` to create, `If-Match` with the
  ETag to update, delete and run, 412 for a stale one and 428 for none; storage writes carry
  `Idempotency-Key` and `X-Yogabase-Content-Sha256`; a job's key is a member of the body. The clients'
  existing tests pin all three.
- **Correlation.** The gateway and the Control Plane answer `X-Correlation-ID` and put
  `correlationId` in a problem; every client reads the header first.
- **The realtime hub.** Methods `Subscribe`, `Unsubscribe`, `TrackPresence`, `UntrackPresence`,
  `GetPresence` and `InvokeLambda`; client methods `message` and `presence`. The .NET client uses
  exactly these names. No other language has a realtime client (below).
- **The runtime-host relay.** The Pod-local relay serves `/runtime-host/v1/self/{heartbeat, ready,
  reserve, shutdown, assignments}` and the assignments page states `headState` and `headSequence`;
  the .NET runtime-host client and the Unity package call those routes and read the head.
- **The Lambda runtime API.** The routes under `/v1/lambda-runtime/` (objects, users, realtime topics
  and user publication, actors, workflows, reminders, topics, streams and queues) are the ones
  `Yogabase.Lambda` calls; none has changed since the wrapper was last held to them.
- **Builds and Delivery.** The build-ingest and Delivery routes have not changed; the mirrors of both
  contracts are identical to the product's.
- **Jobs and Schedules.** The schedule id rule `^[A-Za-z0-9][A-Za-z0-9._~:-]{0,127}$`, both policies
  required, the concurrency policies and the 409 of a manual run of a withdrawn function version are
  the contract the clients already follow; nothing has changed since.

## (e) Capabilities the product has filled

### The .NET client's Data API

`YogabaseClient.Data` (`IYogabaseData`) selects, inserts, upserts, updates and deletes rows of an
exposed table as the signed-in user, under row-level security, through
`POST /v1/data/{table}/select|insert|upsert|update|delete`, and only where the bootstrap's
`data-rest` row is available (otherwise `NotSupportedException` before anything is sent). It checks
the contract's bounds before sending (the name rule, 32 filters, 8 order terms, limit 1 to 1000,
offset to 100,000, 1 to 500 rows, 16 conflict columns, a filter on every update and delete, the
whole document at most 1,114,112 bytes as sent), reads a success strictly and names a refusal by the
gateway's code, with `limitBytes` and `maxBodyBytes` on a 413. `ContractOperationParityTests` now
sends the five Data operations from the .NET client instead of excluding them, and
`DataContractTests` holds the limits, operators, refusal codes and name rule to
`x-yogabase-data-api`. No SQL, function call or role travels from a client.

### `Yogabase.Lambda`'s typed data API and caller connection

`LambdaContext.Data` serializes the runtime's typed data API: `Data.From(table)` for the five
operations, `Data.RpcAsync(function, arguments)` for a database function by its named arguments
(a Lambda only; the client gateway never maps it), and `Data.AsCaller()` for the same requests as the
signed-in caller under row-level security. Each request is one document
`{identity, operation, table|function, request}` handed to the runtime's delegate, with the same
bounds checked first; an answer with a status other than 200 is a `LambdaApiException` with that
status and code, among them `data_caller_identity_unavailable` for `AsCaller()` on an invocation with
no caller. On `net10.0`, `LambdaContext.CallerDatabase` is the caller entry of the runtime's
connection map. Entity Framework Core configuration is not wrapped: it stays server-side, which the
boundary requires of every client SDK.

### The Java sign-in

`YogabaseSignIn.signInWithPassword`, `startExternalSignIn` and `completeExternalSignIn` follow the
flow in (c) with the JDK's own HTTP client (cookies kept, redirects never followed), and
`YogabaseSession` is the Kiota `AccessTokenProvider`: the bearer goes to the gateway origin only and
is refreshed with the rotating refresh token within a minute of expiry.
`YogabaseApplicationClient.forSession` builds the application client for a session. No dependency
was added.

`Yogabase.Lambda`'s data wrapper against them. 40 checks passed: the statement each operation
builds and the identity it runs as (the signed-in user under row-level security for a client, the

without row-level security, a missing table, a column that is not exposed, another project's token

on an invocation with no caller. Not exercised: a database, the project realm's own token
validation, a live installation. The Java sign-in has run only against its fake loopback gateway.

## What remains

- **Realtime outside .NET.** The TypeScript, Python, Java and Dart clients have no realtime client.
  Each would need a SignalR client library as a new dependency and its own platform qualification.
- **Runtime-host modules outside .NET and Unity.** The other languages have none; each may add one
  against the self-scoped relay routes.
- **The relay routes in a contract.** `/runtime-host/v1/self/*` is described by no mirrored
  document; the mirrored runtime-host document is instance-addressed, so relay drift is not caught
  by a contract digest. A product-side document of the self-scoped routes would close it.
- **The Dart Jobs result digest.** Dart's typed send cannot read a response header, so its Jobs
  client does not check `X-Yogabase-Content-Sha256`.
- **Live runs.** The .NET Data client, the Lambda data wrapper and the Java sign-in have not run
  against a live installation.
